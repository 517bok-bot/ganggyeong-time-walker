## 3. 미검증 → 2단계에서 관리자가 채워야 할 것
1. **장소별 위도·경도**: 공식 좌표를 확인하지 못해 `gps: null`입니다. 입력하면 GPS 인증이 바로 켜집니다. 실제 지도의 중심점(36.1586, 127.0136)도 근사값입니다.
2. 장소별 대표 사진, 역사적 배경, 운영 정보.
3. 대추삼형제 개별 이름, 스윗포 상세 설정.
4. 캐릭터 공식 원화와 사용 허가 (`characters.license_status`).
5. 지역 상점 제휴 여부 (`shops.is_official_partner`는 허가 완료 시에만 true).
6. 승인 자료(knowledge_documents)의 지자체·문화관광해설사 최종 검토.

## 4. 게임 설계 결정
- **캐릭터 배치(게임 설정)**: 강이→기억의 등대(수수께끼·오래된 고양이), 갱이→광신석유(갱갱), 콩이→대청상회(깜뚜누들, 맛있는 냄새), 가족 재회→강경모던상회(안내도 힌트), 베리쥬→웰컴센터, 대추삼형제→강경화랑·홍교리·랑만광장. 화면에 "게임 설정"으로 표시합니다.
- **NPC**: 달래·덕배·은솔·만복·포포는 모두 창작 인물이며 실존 인물·상인이 아닙니다. 역사 인물 해설 NPC는 검증 자료 확보 후 추가합니다.
- **NPC 대사 원칙**: 역사·관광 정보는 `knowledge.ts` 승인 자료만 읽어 주고 출처를 표시합니다. 5단계 AI NPC도 이 자료만 근거로 쓰도록 서버에서 호출합니다.
- **실제 vs 온라인 보상 구분**: 현장 방문 30~60 EXP, 온라인 장소 발견 10 EXP. 캐릭터 발견 방식(현장/온라인)은 도감에 따로 기록합니다.
- **젓갈 미니게임 채점(게임 규칙)**: 종류별 '알맞은 소금 비율' 구간 60점 + 넣는 순서(주재료→소금→웃소금) 25점 + 정성 한 스푼 15점. 실제 제조법이 아님을 화면에 표시합니다.
- **숙성 시간**: 실제 시간 기반(새우젓 3분, 멸치젓 5분, 황석어젓 8분). 운영 시 관리자가 늘릴 수 있도록 `fermentation_recipes.aging_minutes`로 분리했습니다.
- **QR 설계**: `GTW1.<장소ID>.<HMAC 16자>`를 `https://도메인/explore?qr=…` URL로 인쇄 → 휴대폰 기본 카메라로도 열립니다. 서명 비밀키는 서버에만 있습니다. 2단계에서 `location_visits` UNIQUE 제약으로 서버 단 중복 보상을 막습니다.
- **위치 권한 거부 시**: QR 인증과 온라인 마을이 그대로 동작합니다. 위치는 인증 순간에만 서버로 보내고 저장하지 않습니다.
- **요청 제한**: 1단계는 메모리 기반(IP당 분당 30회). 다중 인스턴스 배포 시 공유 저장소로 바꿔야 합니다.

## 5. 2단계 결정 사항
- **게임 엔진 하나로 두 모드 지원**: `lib/engine.ts`의 순수 함수가 보상·조건을 모두 계산합니다. 로그인 전에는 브라우저에서, 로그인 후에는 `/api/game/action`에서 같은 코드가 실행됩니다. 클라이언트는 행동 종류만 보내고 보상 값을 보내지 않습니다.
- **저장 구조**: 플레이어 상태 전체를 `game_saves.state`(JSON)에 두고, 무결성과 통계가 필요한 부분은 정규화 테이블(`location_visits`, `collections`, `user_quests`, `user_fermentation`, `community_jar_contributions`)에도 기록합니다. 둘 다 `commit_game_action` 함수 하나가 **한 트랜잭션**으로 처리합니다.
  - `version`이 다르면 거절하고 서버가 최신 상태로 다시 계산합니다(최대 3회). 동시 요청에 의한 이중 보상과 기록 유실을 막습니다.
  - `location_visits (user_id, location_id)` PK로 장소당 1회만 방문 보상을 줍니다. 퀘스트도 `user_quests` PK로 1회만 줍니다.
- **권한**: 진행 테이블은 RLS로 본인 읽기만 허용하고 쓰기 정책은 두지 않았습니다. 서버 전용 함수는 `anon`·`authenticated` 실행 권한을 명시적으로 회수했습니다. Supabase는 public 함수에 이 역할들의 실행 권한을 직접 부여하므로 `public` 회수만으로는 막히지 않는다는 점을 테스트로 확인하고 고쳤습니다. `profiles`도 쓰기 정책이 없어 레벨·코인·역할을 직접 바꿀 수 없습니다.
- **증명 검증**: QR은 서명과 '요청한 장소와 QR의 장소가 같은지'를 서버에서 확인합니다. GPS는 관리자가 등록한 좌표·반경, 정확도 80m 이하 조건으로 서버가 판정합니다. 시연 도구(시뮬레이션·빨리감기)는 서버 모드에서 `DEMO_TOOLS=true`일 때만 허용합니다.
- **로컬 기록 이전 안 함**: 로그인 전 브라우저 기록은 조작할 수 있으므로 서버로 옮기지 않습니다. 게스트(익명) 계정으로 시작한 뒤 이메일을 연결하면 서버 기록은 그대로 이어집니다.
- **QR 링크 진입 경쟁 조건**: QR 링크로 앱이 열리면 세션 확인 전에 인증이 로컬 모드로 실행되는 버그를 E2E로 발견했습니다. 모든 행동이 세션 확인 완료까지 기다리도록 고쳤습니다.
- **관리자 편집 콘텐츠**: 좌표·사진·설명·역사·캐릭터 설정·승인 자료는 DB 값이 코드 기본값을 덮어씁니다(60초 캐시, 저장 시 즉시 무효화). 역사 설명은 '승인' 상태만 공개합니다. 공식 원화는 사용 허가가 '허가 완료'일 때만 임시 그림을 대체합니다.
- **관리자 권한**: `ADMIN_EMAILS` 또는 `profiles.role in ('admin','editor')`. 모든 관리자 페이지와 서버 액션이 요청마다 서버에서 다시 확인합니다.
- **엽서와 개인정보**: 합성은 브라우저에서 합니다. 사용자 사진은 동의 체크 후에만 넣을 수 있고, 800px로 줄여 다시 인코딩해 EXIF 위치정보를 지웁니다. '엽서함 저장'을 누를 때만 비공개 버킷에 올라가며, 공개 여부는 기본 비공개입니다. DB에도 `uses_user_photo → photo_consent` 제약이 있습니다. 엽서 삭제 시 파일도 지우고, 회원 탈퇴 시 파일 삭제 후 계정을 지우며 모든 기록은 cascade로 삭제됩니다.

## 6. 검증 내역 (2단계)
- `npm test`: 엔진 규칙 12건 — 중복 방문, 시연 도구 차단, 잘못된 보상 키, 퀘스트 1회, 젓갈 검증, 퀴즈 판정, 엽서 조건 등.
- `supabase/tests`: 실제 PostgreSQL 16에서 스키마 2회 적용(재실행 안전성), 커밋 함수(버전 충돌·중복 방문 롤백·퀘스트 중복·항아리·공동 기여), RLS(타인 기록 차단, 권한 상승 차단, 서버 함수 직접 호출 차단, 관리자 통계 차단).
- 서버 모드 E2E 32건: 실제 브라우저 + 실제 Next.js 서버 + 실제 PostgreSQL. Supabase 자체 대신 테스트용 대역 서버(`tests/mock-supabase.mjs`)를 사용했습니다. 게스트 가입 → QR 방문 → 위조·재사용·우회 거절 → 동시 요청 → 젓갈 → 공동 항아리 → 퀘스트 → 엽서 업로드 → 관리자 차단·시드·좌표 등록 → GPS 거리·정확도 판정 → 새로고침 유지 → 탈퇴 삭제.
- **실제 Supabase 클라우드 프로젝트에서는 아직 시험하지 못했습니다.** 특히 이메일 매직 링크 발송, Realtime 구독, Storage 정책은 실제 프로젝트 연결 후 확인이 필요합니다.
